### 数据保护与恢复边界

- 本机已有记录优先，整个数据库合并使用事务。损坏照片即使属于冲突记录也必须验证；失败不能留下部分账目。
- 同一支付交易的不同ID先映射，再处理消费和订阅关联；同一期已付款订阅不产生第二笔消费。本机改名的订阅仍可恢复有效付款关联。
- 本机待确认/忽略的支付不因旧备份中的消费记录而被重新记账；恢复去重身份时保留人工修改字段。
- 照片发布、数据库保存、导出和无引用照片清理共享生命周期锁，防止刚恢复的照片被清理。
- 单份备份最多64MB，单张照片最多8MB。采用内存JSON处理，尚不支持大文件分包/流式恢复。旧备份中原本不存在的数据无法补回。
- 恢复不改变系统授权或识别开关。文件丢失、类型错误、版本不支持等会显示失败。

### 提醒边界

- 使用系统非精确闹钟，计划每日9点检查；打开应用及相关记录变化时也检查。系统可能延后，不能作为严格定时保证。
- 停用、已付款不提醒；已删除消费留下的旧付款关联不再错误地屏蔽提醒。
- 同一天去重；修改/付款时更新仍显示的通知；已被划掉的同日通知不会反复弹出。
- 提醒点击打开订阅页，缴费链接仍由用户点击；不会自动付款或确认入账。
- 权限被关闭时不消耗提醒身份，重新允许后可提醒；重启/时间变化/版本升级有恢复入口。系统强行停止后仍需要重新打开应用。

## 小米15无线调试

环境：Android 16 / HyperOS OS3.0.307.0.WOCCNXM；安装的是可调试构建。

1. 升级前保存练呗私有数据副本。0.7.0覆盖升级至0.8.0成功，数据库5→6；升级前后各表数量一致，SQLite完整性检查为`ok`。
2. 最初通知使用权已开，但系统日志明确提示自启动限制阻止监听绑定。常驻服务存在，自检未收到；没有将它误报为监听成功。
3. 用户开启自启动并重新开启通知使用权后，监听实际连接，系统自检通知收到回调。第一次时间戳差约14ms。
4. 用户从最近任务划走练呗后，观测不到页面主进程，采集进程和系统监听绑定存在；包并未处于强行停止状态。再次自检收到回调，时间戳差约22ms，未启动页面主进程。
5. 划走前后两次观察到的采集PID不同，不能据此宣称全程没有中断；本轮没有连续跟踪该过渡或测量恢复空窗。后续约20秒的5次采样为同一采集PID，主进程始终未观测到。
6. 约12分钟后的扩展检查仍看到同一采集进程和系统服务绑定，但ADB自检广播未真正执行。系统日志显示 `Greezer Denial ... need cached broadcast`；自检时间戳没有更新，因此这次不能算回调通过，也不能据此直接判断真实微信通知被阻断。后续需用真实来源的通知验证锁屏/空闲路径。

### 内存快照

`dumpsys meminfo`原值单位为KiB，下表换算为MiB（÷1024）。PSS、RSS、Swap PSS是不同口径，不能把RSS当成独占内存；这些读数不是付款瞬间峰值。

| 状态 | PSS | RSS | Swap PSS |
|---|---:|---:|---:|
| 首次打开页面，页面进程 | 127.99 | 245.70 | 1.57 |
| 同阶段采集进程，尚未绑定监听 | 59.97 | 141.99 | 1.66 |
| 已绑定、划走前，页面进程在后台 | 89.02 | 179.10 | 33.26 |
| 同阶段已绑定采集进程 | 59.35 | 101.76 | 42.63 |
| 页面进程不存在，自检前采集进程 | 61.88 | 98.81 | 41.14 |
| 页面进程不存在，自检后采集进程 | 59.31 | 108.81 | 29.61 |

随后5次空闲样本PSS为44.67、55.90、55.75、55.75、55.74 MiB，反映系统回收/换页下读数会变化。采集进程快照均无Activity、无View，SQL MEMORY_USED为0。前后台双进程同时存在时总开销会更大。

本轮自检验证的是Android通知回调，不是新的一笔微信付款；未要求用户产生消费。真实支付峰值、密码键盘卡顿、锁屏长待机、断网/重启、系统清理和无线调试关闭后的行为仍应另行测量。没有声称永不被系统停止或零后台进程。
