# 0.6.0 支付识别与两级分类验证

日期：2026-10-19。

## 本次实现

- 微信、支付宝通知捕获：支持 text、bigText、textLines；仅保存提取结果与哈希，不保存通知原文。
- 用户手机截图样本：标题“微信支付”，正文“已支付¥22.00”，解析为2200分。商户不从截图内的付款页面推断，通知不含商户时显示“待补充商户”。真实截图不被写入示例账本。
- 通知识别先进入待确认，确认后计入消费；开启/关闭、权限、真实监听连接状态、最近固定诊断原因、重连和监听自检入口。
- 数据库4→5增加通知身份映射，保留原有记录。稳定事件时间或相同交易号的重放与信息补全去重；确认采用事务。
- 九大消费分类及其小类，手动记录和支付确认共用。旧“餐饮”在统计中归入“食品酒水”，饮食关联消费保存对应餐次。
- 参考随手记公开界面的金额优先、分类格和分类路径；沿用练呗主题。截图见 releases/payment-v6/category.png、category-food.png。

## 真机验收与已知限制

后续已在小米15 / HyperOS3 / Android16完成一次真实微信购买验证：读取到“微信支付 / 已支付¥…”，练呗诊断“已加入待确认”，界面出现金额一致的待确认账目。金额和原始通知不随仓库上传。该结果证明单次付款通知接收、解析、持久化与展示链路通过，不代表所有付款场景均已验证。

用户从最近任务划走练呗后，实测进程与服务均不存在；通知使用权仍已授权，但系统实时监听连接中没有练呗。因此当前版本未满足划走后持续监听要求。

此前整个练呗进程的一次RSS快照为168680 KiB（约164.7 MiB），包含UI及共享页；没有采集PSS、监听独占内存、处理峰值。不能据此推算常驻监听最低占用。

用户报告密码键盘出现前有黑色背景/Logo移动，输入期间持续卡顿，原因尚未确认。排查期间未发现残留uiautomator进程；之后已断开电脑ADB连接。手机无线调试开关因系统权限限制无法远程关闭，已告知用户手动关闭。尚未完成监听启停与无线调试开关的对照测试。

退款、转账、红包当前跳过，尚不支持自动退款冲减或红包支出。聊天通知的标题正文不保存；诊断只记录来源、时间和固定原因。

安装后进入“支付待确认 → 识别设置与演示 → 开启自动识别”，授权通知读取并允许提醒，再运行“检查通知监听”。下次真实支付后核对待确认金额、时间和分类，再确认入账。

若来源通知无稳定when且无已知交易号，更新通知的postTime改变后仍可能产生第二条待确认；无法仅靠相同金额/通知key区分更新与另一笔真实支付，因此不做金额模糊合并。用户需核对后只确认一次；系统没有通知或隐藏正文时也无法提取。
